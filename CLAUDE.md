# Инструкция для Claude (Ведущий Архитектор и UI/UX Инженер)

Назначение: глубокий рефакторинг компонентов, разработка логики интерфейса (React 19, CSS Modules),
проектирование структуры данных, написание юнит- и e2e-тестов.

## 0. Начало новой сессии

Перед тем как читать код или начинать задачу, прочитайте в таком порядке:

1. [`../docs/STATUS.md`](../docs/STATUS.md) целиком — актуальное состояние `main`, что влито в
   production, что ожидает `REVIEW PASSED` (секции «Обновление YYYY-MM-DD», новейшие сверху).
2. Последние записи [`../docs/worklog/2026-10.md`](../docs/worklog/2026-10.md) (или текущего
   месяца) — за эту и прошлую календарную дату: детали реализации, которых нет в `STATUS.md`.

Эта папка (`C:\Yury\Jarvis\app`) — общая рабочая копия: над ней параллельно может работать другой
агент (Codex и др.). Если видите в `git reflog`/`git status` следы чужой сессии (неожиданный
`reset`, смена ветки, незнакомые незакоммиченные файлы) — не удаляйте и не перезаписывайте их
не разобравшись; опишите находку в ответе пользователю. Собственные незакоммиченные правки,
которым ещё не дали `REVIEW PASSED`, по той же причине не оставляйте надолго без присмотра —
`git reset --hard`/переключение ветки другим агентом их не пощадит (`git stash` с описанием —
безопаснее, чем просто уйти из сессии).

## 1. Правило работы с кодом

- Всегда соблюдайте чистоту архитектуры: разделяйте логику, UI и дизайн-токены. Не используйте
  захардкоженные стили там, где можно применить CSS-переменные из `src/index.css`.
- При изменении структуры данных или сущностей (например, клиентов и проектов) проверяйте
  связанность зависимостей во всех затронутых компонентах.

## 2. Проверка перед передачей результата

- Перед тем как отдать код на ревью, убедитесь в корректности синтаксиса.
- Обязательно обновляйте или добавляйте unit-тесты (Vitest) и e2e-тесты (Playwright) для нового
  функционала.
- **Definition of Done** — перед КАЖДЫМ отчётом о готовности задачи (даже локально, до
  `REVIEW PASSED`) обязательно:
  1. `npm run verify` и `npx playwright test` зелёные (или явно сказано, что и почему красное);
  2. обновлён [`../docs/STATUS.md`](../docs/STATUS.md) — новая секция «Обновление YYYY-MM-DD»
     сверху (после заголовка, перед предыдущими) с сутью изменения, веткой, тем, что проверено;
  3. добавлена запись в [`../docs/worklog/YYYY-MM.md`](../docs/worklog/) текущего месяца — что
     сделано, какие файлы, какие тесты;
  4. если менялась схема БД или принято архитектурное решение — создан/обновлён ADR в
     [`../docs/decisions/`](../docs/decisions/), со ссылкой на него из `STATUS.md`.

  Пропуск этого шага — не «доделаю потом»: следующий агент (свой или чужой, например Codex в той
  же папке) начинает сессию с чтения `STATUS.md`/`worklog` и не увидит незадокументированную
  работу вообще, даже если код уже в `main`.

## 3. Стек

- Соблюдение стека: React 19, Vite, CSS Modules, Supabase (декларативные схемы, RLS, Edge
  Functions). Использование Tailwind или сторонних UI-библиотек без согласования не допускается.

## 4. Документирование

- Любое значимое архитектурное решение оформляется в виде ADR (Architecture Decision Record) в
  папке `../docs/decisions/` с обновлением `../docs/STATUS.md`. Полный чек-лист перед отчётом о
  готовности задачи — Definition of Done в разделе 2.

## 5. Ограничения

- Claude работает в режиме разработки и проектирования. Прямой деплой в production-среду без
  предварительной верификации тестами и прохождения CI запрещён.

## Практические заметки по этому репозиторию

- **Токены**: цвета, радиусы, размеры шрифта, тени — `src/index.css` (`--radius-*`,
  `--font-size-*`, `--section-*`, `--status-*`, `--shadow-*`, `--ink-*`); тёмная тема и Forest
  переопределяют их в `html[data-theme=…]`. Статусы проектов — `src/utils/projectStatuses.js`.
- **Данные**: доступ к Supabase только через `src/data/*Repository.js`. «Клиент» — не отдельная
  сущность, а группа проектов `clients` с одинаковым `client_name` (`utils/clientGroupRename.js`,
  `dashboardHelpers.groupByClient`). Жизненный цикл проекта — `utils/projectLifecycle.js`.
- **Схема БД**: изменения — новой идемпотентной миграцией в `supabase/migrations/` и синхронно в
  декларативном снимке `supabase/schemas/` (CI собирает базу из снимка и проигрывает миграции
  после `20261010000000`); права проверяются pgTAP-тестами в `supabase/tests/`. Миграция
  применяется к live до деплоя фронтенда, который от неё зависит.
- **Проверка**: `npm run verify` (lint, Vitest, build) и `npm run test:e2e`; Supabase в e2e
  замокан (`e2e/support/supabaseMock.js`).
- **Файлы**: окончания строк CRLF; не менять состояние последнего перевода строки в файле.
- **Документация**: значимые изменения — запись в `../docs/worklog/`, трудно обратимые решения —
  ADR в `../docs/decisions/`. В документацию не попадают ключи, токены, пароли и персональные
  данные клиентов.
